# 모기 예보

기상 데이터를 모기 활동 예측으로 바꿔 주는 서비스.

기온·습도·바람 세 값으로 100점 만점의 **모기활동지수**를 계산하고, 서울시 모기예보제와 같은
4단계(쾌적·관심·주의·불쾌)로 나눠 보여 준다. 기온과 날씨 아이콘을 띄우는 데서 끝내지 않고
"오늘 이 지역에 모기가 얼마나 활동하는가", "그래서 무엇을 해야 하는가"까지 이어지도록 만들었다.

점수 산출 근거는 서울시 모기예보제와 곤충학 자료를 따랐고, 그 근거를 소개 화면에서 그대로 밝힌다.

- Github 주소: https://github.com/SangMyeong5426/skala-vue
- 배포 주소: https://skala-vue-mauve-seven.vercel.app/

## 화면 구성

| 경로               | 화면        | 하는 일                                                      |
| ------------------ | ----------- | ------------------------------------------------------------ |
| `/`                | 서비스 소개 | 첫 화면. 모기 매개 감염병, 예방 수칙, 점수 산출 방식과 근거  |
| `/dashboard`       | 대시보드    | 도시별 지수 카드 비교, 검색·정렬·즐겨찾기, 주간 예보, 대기질 |
| `/mosquito`        | 도시 랭킹   | 전체 도시를 점수순으로 세우고 항목별 근거를 나란히 비교      |
| `/weather/:cityId` | 지역 상세   | 한 도시의 점수 근거와 관측값                                 |
| 그 외              | 페이지 없음 | 정의되지 않은 경로 처리                                      |

# 개발 과정

처음부터 지금 형태였던 것이 아니라, 화면 하나에서 시작해 기능을 붙이고 구조를 여러 번 갈아엎으며 지금에 도달했다. 아래는 그 순서다.

## 1. 기본 날씨 화면

시작은 화면 하나였다. 도시 배열을 직접 적어 두고 `v-for`로 카드를 찍어 낸 뒤,
입력창에 친 글자로 목록을 걸러 내는 정도.

지금 코드에도 그때 골격이 남아 있다. `WeatherHomeView.vue`가 `v-for`로 `WeatherCard`를 반복하고,
`v-if` / `v-else`로 세 가지 상태를 갈라 놓는다. 불러오는 중인지, 검색 결과가 비었는지,
즐겨찾기만 켰는데 해당하는 도시가 없는지에 따라 다른 화면이 나온다.
세 경우가 모두 "카드가 안 보인다"는 같은 결과인데도 사용자가 다음에 할 일이 다르기 때문에
각각 다른 안내를 띄운다.

검색 입력은 `v-model` 대신 `:value` + `@input`으로 묶었다. 한글은 조합이 끝나기 전에도
입력 이벤트가 발생하는데, `v-model`은 조합 중 값을 잡아 두는 구간이 있어 목록 필터가
한 박자 늦게 반응한다. 값을 직접 내려 주고 이벤트를 직접 받으면 첫 글자부터 목록이 즉시 걸러진다.

카드 하나가 담는 내용도 이 단계에서 정해졌다. 도시 이름과 날씨 아이콘, 지수와 등급,
그 아래 기온·습도·바람. 지수를 맨 위에 두고 원본 관측값을 아래에 깐 것은
"이 앱은 날씨 앱이 아니라 모기 앱"이라는 것을 카드 한 장에서 드러내기 위해서다.

`weatherMock.js`는 지금도 남아 있지만 역할이 바뀌었다. 처음에는 화면에 뿌릴 유일한 데이터였고,
지금은 API 호출이 실패했을 때만 쓰이는 대체 데이터다. 실제 도시 목록과 같은 다섯 곳으로
맞춰 두어 온라인이든 오프라인이든 같은 도시가 보인다.

| 기본 구조                 | 이 프로젝트에서 바꾼 것                                       |
| ------------------------- | ------------------------------------------------------------- |
| 배열을 `v-for`로 출력     | 지수를 카드 머리로 올리고 관측값을 근거로 아래 배치           |
| `v-model`로 검색어 바인딩 | 한글 조합 중에도 목록이 반응하도록 `:value` + `@input`        |
| 결과 없음 화면 하나       | 로딩 / 검색 결과 없음 / 즐겨찾기 없음을 각각 다른 안내로 분기 |
| Mock은 초기 데이터        | 실패 시 대체 데이터로 역할 변경, 실제 도시 목록과 동기화      |

## 2. Composition API로 정리

화면이 커지면서 값이 값을 낳기 시작했다. 검색어가 바뀌면 목록이 바뀌고, 목록이 바뀌면
평균 점수가 바뀌고, 평균이 바뀌면 요약 카드의 등급 색이 바뀐다. 이 연쇄를 손으로 갱신하는 대신
파생 관계로 선언했다.

핵심은 `WeatherHomeView.vue`의 목록 파이프라인이다.

```
weatherList          Store의 전체 도시
      ↓ 검색어로 이름 필터
filteredWeatherList
      ↓ 즐겨찾기만 보기 + 정렬 기준·방향 적용
visibleWeatherList
      ↓ 평균·최고·최저·최악 도시 집계
weatherSummary       요약 카드
```

네 단계가 전부 `computed`다. 어디서 무엇이 걸러지는지가 이름만 봐도 드러나고,
중간 단계를 각각 다른 곳에서 쓸 수 있다. 검색 결과가 비었는지는 `filteredWeatherList`로 판단하고,
즐겨찾기 때문에 빈 것인지는 `visibleWeatherList`로 판단한다. 한 덩어리로 합쳤다면 둘을 구분할 수 없다.

정렬은 값 종류가 세 갈래라 비교 함수를 따로 뒀다. 이름은 문자열 비교, 기온·미세먼지는
데이터에 있는 숫자, 모기활동지수는 데이터에 없고 그때그때 계산해야 하는 값이다.
`city[sortKey]`로 꺼낼 수 없는 지수 때문에 비교값을 뽑는 함수를 한 자리에 모았다.

`ref`는 사용자가 직접 건드리는 값에만 쓴다. 검색어, 선택한 도시, 정렬 기준과 방향,
즐겨찾기 목록, 자동 갱신 스위치. 나머지는 전부 이 값들에서 파생된다.

`watch`는 값이 바뀐 뒤 부수 효과가 필요한 곳에 썼다. 즐겨찾기 배열이 바뀌면 `localStorage`에 저장한다.
저장은 화면을 다시 그리는 일과 상관없으므로 `computed`가 아니라 `watch`가 맞는 자리다.

`watchEffect`는 어떤 값을 지켜볼지 미리 적지 않아도 되는 점을 이용해,
검색어가 바뀔 때마다 현재 필터 상태를 콘솔에 남기는 데 썼다.

자동 갱신은 `onMounted`에서 5분 타이머를 걸고 `onUnmounted`에서 반드시 해제한다.
해제를 빠뜨리면 화면을 떠난 뒤에도 타이머가 계속 돌면서 API를 부른다.

| 기본 구조                     | 이 프로젝트에서 바꾼 것                                          |
| ----------------------------- | ---------------------------------------------------------------- |
| 목록 하나를 `computed`로 필터 | 필터 → 즐겨찾기 → 정렬 → 집계를 4단계로 쪼개 각 단계를 따로 활용 |
| `city[sortKey]`로 정렬값 접근 | 계산으로만 얻는 지수를 위해 비교값 추출 함수를 별도로 둠         |
| `watch`로 화면 갱신           | 화면 갱신은 `computed`, 저장 같은 부수 효과만 `watch`            |

## 3. 컴포넌트로 분리

한 파일이 화면 전체를 담고 있어 어디를 고쳐야 무엇이 바뀌는지 알기 어려워졌다.
기준을 "이 조각이 자기 데이터를 직접 가져오는가, 받아서 그리기만 하는가"로 잡고 잘랐다.

`BaseDashboardCard.vue`는 카드 껍데기만 담당한다. 테두리·제목 줄·접기 버튼을 갖고 있고
내용은 `slot`으로 받는다. 제목은 이름 있는 슬롯이고, 접힘 상태를 슬롯 속성으로 내려 준다.
그래서 카드가 접혀 있을 때만 제목 옆에 요약을 덧붙이는 식이 가능하다.
대시보드의 검색·목록·요약·예보·대기질이 전부 이 껍데기를 쓴다.

`SearchBar.vue`는 검색어를 `props`로 받고 `update-query`로 되돌려 준다.
값을 자기 안에 두지 않고 위로 올린 이유는, 같은 검색어를 목록 필터와 빈 화면 안내가
함께 써야 하기 때문이다.

`WeatherCard.vue`는 이벤트를 네 개 올린다. `select-card`, `click-detail`,
`toggle-favorite`, `remove-city`. 이 중 앞의 둘을 굳이 나눈 것이 이 화면의 중심 동작이다.

- 카드 본문을 누르면 `select-card` — 화면을 옮기지 않고, 그 자리에서 카드가 펼쳐지며
  기온·습도·바람이 각각 몇 점을 냈는지 보여 준다.
- 카드 안 버튼을 누르면 `click-detail` — 상세 화면으로 넘어간다.

한 카드 안에 두 동작이 겹쳐 있으므로 별표·삭제·상세 버튼은 모두 `@click.stop`으로
카드 클릭이 같이 발생하지 않게 막았다.

`FilterControlBar.vue`는 정렬 기준·방향·즐겨찾기 스위치만 갖는다. 상태는 하나도 갖지 않고
현재 값을 받아 표시하고 변경을 올려 보내기만 한다.

`AirQualityList.vue`와 `ForecastPanel.vue`는 도시 목록 또는 도시 하나를 받아 그리는 조각이다.
`ForecastPanel`은 받은 예보 5일에 각각 지수를 매겨, 그중 가장 높은 날을 찾아 한 줄로 알려 준다.

`UnitToggler.vue`는 예외적으로 부모에게 이벤트를 올리지 않고 Store를 직접 쓴다.
표시 단위는 특정 화면의 상태가 아니라 앱 전체 설정이라, 헤더에 두고 어느 화면에서든
같은 값을 바라보게 하는 편이 맞았다.

점수 계산은 컴포넌트에 넣지 않고 `mosquitoScore.js`로 뺐다. 같은 계산을
카드·요약·상세·랭킹·주간 예보가 함께 쓰는데, 어느 한 컴포넌트에 있으면 나머지가 그 컴포넌트를
불러야 한다. 화면과 무관한 순수 함수 모듈로 두면 "도시"가 아니라 "예보 하루치"를 넣어도
같은 함수가 그대로 동작한다. 지금 예보 패널이 하는 일이 정확히 그것이다.

스타일은 각 컴포넌트의 `<style scoped>`로 옮기고, 색·간격·모서리 같은 공용 값만
`assets/exercise.css`에 토큰으로 남겼다.

```
하나의 큰 화면
      ↓
검색 / 카드 / 정렬 / 목록 / 예보 / 공통 껍데기로 분리
      ↓
계산 로직은 화면 밖 모듈로, 스타일은 컴포넌트 안으로
```

| 기본 구조                 | 이 프로젝트에서 바꾼 것                                              |
| ------------------------- | -------------------------------------------------------------------- |
| 카드 클릭 = 상세 이동     | 선택과 이동을 두 이벤트로 분리, 선택은 제자리 펼침으로 처리          |
| 계산을 컴포넌트 안에서    | 여러 화면이 공유하므로 순수 함수 모듈로 분리, 예보 하루치에도 재사용 |
| 자식은 항상 이벤트를 올림 | 앱 전역 설정인 표시 단위만 예외로 Store 직접 사용                    |
| 슬롯으로 내용만 전달      | 접힘 상태를 슬롯 속성으로 내려 접었을 때 제목에 요약 표시            |

## 4. Vue Router로 화면 나누기

카드에서 상세보기를 누르면 경고창이 뜨는 정도였다. 보여 줄 내용이 늘면서
한 화면에 다 넣을 수 없게 되어 화면을 나눴다.

`App.vue`에 `RouterLink` 세 개로 내비게이션을 두고 `RouterView`를 본문 자리에 놨다.
헤더와 단위 전환은 껍데기에 남아 어디서든 유지된다.

상세 화면은 `/weather/:cityId` 동적 경로다. 카드의 상세보기는 `router.push`로 이동한다.
돌아가기 버튼은 목적지를 정해 보내지 않고 `router.back()`을 쓴다.
대시보드에서 왔는지 랭킹에서 왔는지 모르는데 목적지를 고정하면 엉뚱한 곳으로 가기 때문이다.

**첫 화면을 대시보드가 아니라 소개로 잡았다.** 이 앱의 숫자는 처음 보는 사람에게
"63점"이 무슨 뜻인지 알 수 없다. 무엇을 계산하는지, 근거가 무엇인지 먼저 읽고
데이터로 들어가는 순서가 자연스럽다. 대신 소개 화면이 막다른 길이 되지 않도록
제목 옆과 맨 아래 두 곳에 대시보드로 가는 버튼을 뒀다.

경로를 바꾸면서 이전 주소인 `/about`은 지우지 않고 `/`로 보내는 redirect로 남겼다.

로딩 방식은 첫 화면만 정적으로 불러오고 나머지는 필요할 때 내려받는다.
소개 화면은 진입 즉시 필요하므로 지연 로딩의 이점이 없고, 나머지 세 화면은
방문하지 않으면 받을 이유가 없다.

잘못된 도시 코드는 두 겹으로 막는다. 라우터의 `beforeEnter`가 진입을 검사하고,
화면 안에서는 `onBeforeRouteUpdate`가 검사한다. 둘 다 필요한 이유는
`/weather/city_seoul`에서 `/weather/city_busan`으로 넘어갈 때 같은 컴포넌트가 재사용되어
`onMounted`가 다시 실행되지 않기 때문이다. 이 처리가 없으면 주소만 바뀌고
화면은 이전 도시 데이터가 그대로 남는다. 주소창 직접 수정이나 브라우저 뒤로 가기가 여기에 해당한다.

정의되지 않은 경로는 맨 마지막에 둔 `catch-all`이 받는다. 목록 위쪽에 두면
모든 경로를 먼저 삼켜 버린다.

```
카드의 상세보기 (경고창)
      ↓
동적 경로를 가진 별도 상세 화면
      ↓
소개 / 대시보드 / 랭킹 / 상세 / 404 다섯 화면
```

| 기본 구조                   | 이 프로젝트에서 바꾼 것                                              |
| --------------------------- | -------------------------------------------------------------------- |
| 첫 화면 = 대시보드          | 근거를 먼저 읽히도록 소개를 첫 화면으로, 대시보드는 `/dashboard`     |
| 돌아가기 = 특정 경로로 이동 | 어디서 왔는지 모르므로 `router.back()`                               |
| 경로 변경 시 이전 주소 삭제 | 기존 링크가 살아 있도록 redirect로 유지                              |
| 진입 시 한 번만 검사        | 컴포넌트 재사용 구간까지 막기 위해 진입 가드와 갱신 가드를 함께 사용 |

## 5. Pinia로 상태 옮기기

화면이 나뉘자 문제가 드러났다. 대시보드와 랭킹이 같은 도시 데이터를 필요로 하는데
둘은 부모-자식 관계가 아니라 `props`로 내려 줄 수 없다. 각자 불러오면 화면을 오갈 때마다
같은 호출을 반복하고, 두 화면이 서로 다른 시각의 데이터를 보여 준다.

**`weatherStore`** — 도시 데이터와 검색을 맡는다.

- 상태: `cities`, `addedCities`, `searchResults`, `isLoading`, `isSearching`,
  `errorMessage`, `isOffline`, `lastUpdatedAt`
- 파생: `isReady`(데이터가 하나라도 있는지), `lastUpdatedLabel`(갱신 시각 표기)
- 동작: `fetchAll`, `ensureLoaded`, `loadCityDetail`, `search`, `clearSearch`,
  `addCity`, `removeCity`, `restoreAdded`

`ensureLoaded`가 이 구조의 핵심이다. 이미 받아 둔 데이터가 있으면 호출을 건너뛴다.
대시보드와 랭킹이 각자 진입 시점에 이걸 부르지만 실제 호출은 처음 한 번만 일어난다.

`fetchAll`은 기본 도시와 사용자가 추가한 도시를 함께 불러 한 배열로 합친다.
실패하면 `isOffline`을 세우고, 아직 아무 데이터도 없을 때만 대체 데이터를 채운다.
이미 데이터가 있으면 유지한다. 자동 갱신이 한 번 실패했다고 보고 있던 화면이
대체 데이터로 뒤집히면 곤란하기 때문이다.

**`configStore`** — 표시 단위만 맡는다.

- 상태: `unit`
- 파생: `unitSymbol`
- 동작: `toDisplayTemp`, `toggleUnit`, `restoreUnit`

단위는 여러 곳에서 동시에 읽힌다. 카드·요약·상세·랭킹·예보가 전부 `toDisplayTemp`를 거쳐
기온을 그린다. Store 안에 `watch`를 두어 값이 바뀌면 바로 `localStorage`에 저장하므로
호출하는 쪽에서 저장을 신경 쓸 필요가 없다.

새로고침해도 남는 값은 세 가지이며 저장 주체가 서로 다르다.

| 값                   | 저장 키                     | 저장 주체         |
| -------------------- | --------------------------- | ----------------- |
| 사용자가 추가한 도시 | `skala-vue:added-cities`    | `weatherStore`    |
| 섭씨/화씨 설정       | `skala-vue:temp-unit`       | `configStore`     |
| 즐겨찾기             | `skala-vue:favorite-cities` | `WeatherHomeView` |

즐겨찾기는 대시보드 한 화면에서만 쓰이므로 일부러 Store로 올리지 않고 화면에 뒀다.
저장은 모두 `try` / `catch`로 감쌌다. 저장소를 못 쓰는 환경에서 앱 전체가 멈추면 안 된다.

| 기본 구조                   | 이 프로젝트에서 바꾼 것                           |
| --------------------------- | ------------------------------------------------- |
| 화면마다 데이터 조회        | `ensureLoaded`로 이미 받은 데이터가 있으면 건너뜀 |
| 실패하면 대체 데이터로 교체 | 이미 데이터가 있으면 유지, 없을 때만 대체         |
| 모든 상태를 Store로         | 한 화면만 쓰는 즐겨찾기는 화면에 남김             |
| 저장은 호출부에서           | Store 안 `watch`가 값 변경을 감지해 저장          |

## 6. 직접 적은 데이터에서 실제 API로

가장 큰 변화. 손으로 적어 둔 값을 지우고 실제 관측 데이터를 쓰기 시작했다.
호출과 응답 가공은 전부 `api/weatherApi.js` 한 파일에 모아, Store와 화면은
"어떤 주소를 어떻게 부르는지" 모르게 했다.

### 부르는 곳과 쓰는 값

도시 하나에 세 개를 **동시에** 부른다. 하나가 끝나야 다음을 시작하는 방식이면
도시 다섯 곳에 열다섯 번을 줄 세우게 되어 화면이 뜨기까지 시간이 그만큼 곱해진다.
동시에 부르면 가장 느린 응답 하나만큼만 기다린다.

| 엔드포인트        | 꺼내 쓰는 값                                                              | 화면에서 쓰이는 곳                        |
| ----------------- | ------------------------------------------------------------------------- | ----------------------------------------- |
| `/weather`        | 기온, 체감 기온, 날씨 코드, 날씨 설명 원문, 습도, 풍속, 관측 시각, 시간대 | 카드·상세의 관측값, 지수 계산의 세 입력값 |
| `/air_pollution`  | PM10                                                                      | 대기질 목록, 상세의 미세먼지              |
| `/forecast`       | 3시간 간격 목록, 도시 시간대                                              | 주간 예보                                 |
| `/geo/1.0/direct` | 위도, 경도, 한글 지명, 시도명, 국가 코드                                  | 도시 검색                                 |

응답에서 실제로 쓰는 값만 꺼내 화면이 쓰기 좋은 형태로 다시 만든다.
화면 컴포넌트는 OpenWeatherMap의 응답 구조를 전혀 모른다.

### 날씨 표현을 정리한 이유

응답의 한글 설명은 "온흐림", "튼구름", "실 비"처럼 표현이 제각각이라 그대로 쓰면
아이콘 대응과 상태 분기가 조용히 실패한다. 그래서 설명 문구가 아니라 **날씨 코드**로 판단해
맑음·구름·흐림·비·눈 다섯 가지로 정리했다. 원문은 버리지 않고 상세 화면에 함께 표시해
어떤 응답이 어떻게 정리됐는지 확인할 수 있게 했다.

### 3시간 예보를 하루 단위로

예보 응답은 3시간 간격이라 하루에 여덟 덩어리가 온다. 이것을 하루 한 줄로 줄이는데,
`dt`에 도시 시간대를 더해 현지 날짜로 묶는 것이 먼저다. 이 처리를 빠뜨리면
한국의 오전이 전날로 밀린다.

날짜별로 묶은 뒤 기온은 그날 최고값을 쓰고, 날씨·습도·풍속은 정오에 가장 가까운 시각의 값을 쓴다.
최고 기온은 그날이 얼마나 더웠는지를 대표하고, 습도와 바람은 하루 평균보다
활동 시간대의 값이 의미 있기 때문이다.

여기서 예상하지 못한 소득이 있었다. 예보 응답에 이미 습도와 풍속이 들어 있어
**추가 호출 없이** 예보 5일에도 지수를 매길 수 있었다. 주간 예보가
"이번 주 언제가 가장 심한가"를 알려 주는 기능은 이 덕분에 나왔다.

### 도시 검색

지명 검색은 좌표를 얻는 별도 엔드포인트를 쓴다. 검색어에 국가 코드를 붙이고
응답에서도 한 번 더 걸러 국내 도시만 남긴다. 이름은 한글 지명이 있으면 그것을 쓰고
없으면 원래 이름을 쓴다.

검색으로 추가한 도시는 이름이 아니라 좌표로 식별한다. 목록에 미리 없는 도시라
고정된 코드를 붙일 수 없기 때문에 좌표를 반올림해 만든 코드를 쓴다.
이 코드가 상세 화면 주소가 되므로 다시 열어도 같은 도시가 나온다.

### 실패했을 때

키가 없거나 호출이 실패하면 콘솔 오류로 끝내지 않는다. 상황에 맞는 안내 문구를 만들고,
아직 화면에 아무 데이터도 없을 때만 `weatherMock.js`가 다섯 도시를 채운다.
대체 데이터로 그리는 중이라는 사실은 화면 상단 띠로 계속 알린다.

키는 코드에 적지 않고 환경 변수로 읽는다. `.env.local`은 저장소에 올라가지 않는다.

```
도시 목록 (기본 다섯 곳 + 검색으로 추가한 곳)
      ↓
현재 날씨 / 대기질 / 예보 동시 호출
      ↓
필요한 값만 추출하고 날씨 표현 정리, 예보를 하루 단위로 축약
      ↓
기온 · 습도 · 바람
      ↓
모기활동지수 산출 (100점)
      ↓
4단계 판정과 행동 안내
```

| 기본 구조                  | 이 프로젝트에서 바꾼 것                                     |
| -------------------------- | ----------------------------------------------------------- |
| 화면에서 직접 호출         | 호출·가공을 한 파일로 모아 화면은 응답 구조를 모름          |
| 응답을 순서대로 호출       | 도시당 세 개를 동시에 호출                                  |
| 한글 설명 문구로 상태 판단 | 표현이 제각각이라 날씨 코드로 판단, 원문은 상세에 함께 표시 |
| 예보는 기온만 표시         | 응답에 든 습도·풍속을 활용해 추가 호출 없이 5일치 지수 산출 |
| 실패 시 오류 화면          | 데이터가 없을 때만 대체 데이터, 있으면 유지하고 안내만 표시 |

## 7. UI 라이브러리 적용

직접 만들던 요소 중 일부를 Element Plus로 바꿨다. 전부 바꾸지 않고 기준을 나눴다.

**라이브러리에 맡긴 것** — 동작이 표준적이고 직접 만들면 상태 처리가 번거로운 것.
정렬 선택(`el-select`, `el-option`), 즐겨찾기 스위치(`el-switch`), 버튼(`el-button`),
로딩 자리표시(`el-skeleton`), 빈 목록 안내(`el-empty`).

**직접 만든 것** — 이 앱의 의미가 담기는 요소.
지수 카드, 점수 게이지, 등급 배지, 검색창과 자동완성 목록, 카드 껍데기.
지수 게이지는 점수에 따라 색이 4단계로 바뀌고 등급 배지와 색을 맞춰야 하는데,
라이브러리 컴포넌트의 기본 색 체계에 이걸 억지로 끼우면 규칙이 흐트러진다.

색을 쓰는 규칙도 이 단계에서 정리했다. 흰 바탕에 검은 글자를 기본으로 두고
정보의 위계는 여백과 글자 굵기로 만든다. **색은 등급 네 단계에만 쓴다.**
녹색·파랑·주황·빨강 네 가지가 화면에서 색을 가진 거의 유일한 요소라
숫자를 읽기 전에 상태가 먼저 눈에 들어온다. 다른 곳에도 색을 쓰면 정작 중요한 등급이 묻힌다.

| 기본 구조                   | 이 프로젝트에서 바꾼 것                                   |
| --------------------------- | --------------------------------------------------------- |
| 라이브러리로 화면 전체 구성 | 표준 입력 요소만 라이브러리, 의미가 담긴 요소는 직접 제작 |
| 라이브러리 기본 색 사용     | 등급 4색을 직접 정의하고 그 외에는 색을 쓰지 않음         |

## 8. 하나의 서비스로

앞의 단계들이 합쳐지면서, 날씨를 보여 주는 화면이 **날씨로 모기 활동을 판단하고
행동을 안내하는 서비스**가 됐다.

소개 화면에서 시작한다. 모기 매개 감염병과 예방 수칙을 먼저 보여 주고,
기온 50점·습도 30점·바람 20점이라는 배점과 왜 더울수록 나쁜 것이 아닌지를 설명한다.
기온 점수는 28도 부근이 꼭짓점인 산 모양이라 단순 증가 함수로 표현할 수 없다.
바람은 관측 풍속을 그대로 쓰지 않고 0.6을 곱해 쓴다. 기상관측은 지상 10미터에서 재지만
모기는 사람 키 높이에서 날기 때문이다.

대시보드에서는 다섯 도시를 카드로 비교한다. 검색창에 글자를 치면 목록이 걸러지고,
엔터를 누르면 새 도시를 찾아 추가할 수 있다. 추가한 도시는 저장돼 다음에 다시 와도 남는다.
정렬 기준을 지수·기온·미세먼지·이름 중에 고르거나 즐겨찾기만 볼 수 있다.

카드를 누르면 그 자리에서 펼쳐지며 세 항목이 각각 몇 점을 냈고 왜 그런지 알려 준다.
점수 옆의 설명은 점수와 어긋나지 않도록 맞춰 두었다. 바람 설명은 풍속이 아니라
산출된 점수로 고르는데, 풍속으로 나누면 점수가 0에 가까워지는 구간에서
"크게 방해"와 "날지 못함"이 같은 점수로 겹치기 때문이다.

더 보고 싶으면 상세 화면으로 넘어간다. 기온·습도·바람 세 장의 카드에
실측값·점수·게이지·설명이 한 칸씩 모여 있고, 그 밖의 관측값은 아래에 따로 둔다.

도시 랭킹은 전체를 점수순으로 세워 항목별 근거를 나란히 놓는다.
대시보드가 "각 도시가 몇 점인가"를 본다면 랭킹은 "어디가 가장 심한가"를 본다.

주간 예보는 앞으로 5일에 같은 계산을 적용해 어느 요일이 가장 심한지 알려 준다.

이 밖에 대기질 목록, 섭씨/화씨 전환, 5분 주기 자동 갱신이 있다.

```
소개 화면에서 계산 방식과 근거 확인
      ↓
도시 목록 (기본 다섯 곳 + 검색으로 추가)
      ↓
현재 날씨 / 대기질 / 예보 동시 호출
      ↓
기온 · 습도 · 바람 추출
      ↓
모기활동지수 산출 (100점) → 4단계 판정
      ↓
카드 · 랭킹 · 상세 · 주간 예보에 표시
      ↓
등급별 행동 안내
```

| 기본 구조               | 이 프로젝트에서 바꾼 것                                        |
| ----------------------- | -------------------------------------------------------------- |
| 관측값을 그대로 보여 줌 | 세 값을 하나의 지수로 합치고 4단계 판정과 행동 안내까지 연결   |
| 숫자만 제시             | 무엇이 몇 점을 냈고 왜 그런지를 카드·상세·랭킹에서 함께 표시   |
| 계산 방식은 내부에만    | 산출식과 근거를 소개 화면에 공개하고 반영하지 못한 한계도 명시 |
| 현재 시점만 표시        | 예보 응답을 재활용해 앞으로 5일 중 가장 심한 날까지 제시       |

## 전체 변화

```
        ↓

        ↓

        ↓
07. UI 라이브러리       표준 요소는 라이브러리, 등급 표현은 직접 제작
        ↓
08. 모기 예보 완성      날씨 조회에서 행동 안내까지
```

| 습도 | 30   | 60퍼센트를 경계로 기울기가 달라지는 두 구간           |
| 바람 | 20   | 관측 풍속에 0.6을 곱한 값 기준. 초속 2.2미터에서 0점  |

추운 날 습도와 바람만으로 점수가 올라가지 않도록, 총점에 기온 점수를 따라가는 상한을 둔다.

## 트러블슈팅 정리

만들면서 실제로 겪었던 문제들. 원인을 찾는 데 시간이 걸렸거나, 원인이 예상과 달랐던 것 위주로 남긴다.

### 화면이 깨진 경우

**본문이 화면 왼쪽 절반에만 그려졌다.**
직접 쓴 스타일에는 원인이 없었다. 프로젝트를 만들 때 딸려 온 `assets/main.css`에
`#app`을 1024px 이상에서 두 칸 그리드로 만드는 규칙이 있었고, 내가 만든 레이아웃이
그 첫 칸 안에 갇혀 있었다. `assets/exercise.css`에서 `body`와 `#app`의
`display`, `max-width`, `grid-template-columns`를 원래대로 되돌리는 규칙을 두어 해결했다.

**검색 결과 목록이 아래 카드에 가려 보이지 않았다.**
`z-index`를 올려도 소용이 없었다. 원인은 카드에 걸어 둔 `backdrop-filter`였다.
이 속성은 새 쌓임 맥락을 만들기 때문에, 그 안에서 아무리 높은 `z-index`를 줘도
바깥 형제 요소를 넘어설 수 없다. 검색 카드 자체에 `position: relative`와 `z-index`를 줘서
같은 맥락 안에서 순서를 정하도록 바꿨다.

**상세 화면에서 점수와 등급이 아예 보이지 않았다.**
요소는 렌더되고 있었다. 카드에 `color: #ffffff`만 있고 배경을 지정하는 규칙이 없어서
흰 바탕에 흰 글씨였다. 등급별 배경색을 넣는 대신, 흰 카드에 등급 색 왼쪽 테두리를 두고
글자색을 등급 색으로 주는 쪽으로 바꿨다.

**한글이 단어 중간에서 잘렸다.**
"입으세 / 요"처럼 끊겼다. 기본 줄바꿈 규칙이 한글을 글자 단위로 자르기 때문이다.
`body`에 `word-break: keep-all`을 주어 어절 단위로 끊기게 했다.

### 점수가 이상했던 경우

**기온 18도를 경계로 점수가 47점 튀었다.**
17.9도는 20점, 18.0도는 67점이 나왔다. 추운 날 습도와 바람만으로 점수가 오르는 것을 막으려고
"기온이 낮으면 총점을 20점으로 자른다"는 조건을 뒀는데, 이 상한 자체가 계단이라
경계에서 그대로 튀어 올랐다. 상한을 고정값이 아니라 기온 점수를 따라 움직이는 값
(`5 + 기온점수 × 1.9`)으로 바꿔 최대 차이를 3점으로 줄였다.

**대부분의 도시가 습도 만점을 받았다.**
여름철 한국 습도는 대체로 높은 쪽에 몰려 있는데, 습도 점수를 한 구간 직선으로 만들어 두니
88퍼센트 이상이 전부 같은 점수가 됐다. 도시 간 차이가 사라진 것이다.
60퍼센트를 경계로 기울기가 다른 두 구간으로 나눠, 높은 습도 안에서도 순위가 갈리게 했다.

**바람 설명과 점수가 서로 어긋났다.**
"바람이 활동을 크게 방해합니다"라고 쓰여 있는데 점수는 0점이라, 바로 위 단계인
"바람이 강해 날지 못합니다"와 구분되지 않았다. 설명을 풍속 값으로 나눴기 때문인데,
점수는 0을 향해 연속으로 줄어들어서 풍속 어디에 선을 그어도 그 구간의 윗부분은 결국 0이 된다.
경계를 옮기는 것으로는 풀리지 않아, 설명을 풍속이 아니라 **산출된 점수**로 고르도록 바꿨다.
화면에 찍히는 숫자와 같은 값으로 문구를 정하므로 이제 어긋날 수 없다.

### API 응답을 다루며 생긴 경우

**예보 날짜가 하루씩 밀렸다.**
응답의 시각은 UTC 기준이라, 한국 시간 오전에 해당하는 항목이 전날로 묶였다.
`dt`에 응답이 함께 주는 도시 시간대를 더해 현지 시각으로 바꾼 뒤 날짜별로 묶어 해결했다.
현재 관측 시각을 표시할 때도 같은 처리가 필요했다.

**날씨 아이콘과 상태 분기가 조용히 실패했다.**
오류가 나지 않고 그냥 기본값으로 빠졌다. 응답의 한글 설명이 "온흐림", "튼구름", "실 비"처럼
표현이 제각각이라 앱에서 쓰는 다섯 가지와 하나도 일치하지 않았기 때문이다.
설명 문구 대신 **날씨 코드**로 판단하도록 바꿨다. 원문은 버리지 않고 상세 화면에 함께 표시해
어떤 값이 어떻게 정리됐는지 확인할 수 있게 했다.

**호출이 실패하면 대체 데이터에서 바람이 항상 만점이었다.**
대체 데이터에 `wind` 값을 아예 넣지 않아서, 계산 함수가 `?? 0`으로 0을 받고
"바람 없음 = 20점"으로 처리하고 있었다. 오류도 경고도 나지 않아 늦게 발견했다.
다섯 도시에 풍속을 넣어 실제와 비슷한 점수가 나오게 했다.

**호출이 실패하면 목록에 없던 도시가 나타났다.**
실제 도시 목록과 대체 데이터의 도시가 서로 달라서, 온라인일 때와 오프라인일 때
보이는 도시가 바뀌었다. 두 목록을 같은 다섯 곳으로 맞췄다.

**저장소에 접근할 수 없는 환경에서 화면 전체가 멈췄다.**
`localStorage`를 바로 호출한 곳이 예외를 던지면서 그 위쪽 렌더링까지 같이 죽었다.
저장과 복원을 모두 `try` / `catch`로 감싸, 저장을 못 하더라도 앱은 계속 동작하게 했다.

**갱신 한 번에 API를 51번 불렀다.**
도시를 열일곱 곳 두었는데 도시마다 세 개를 부르니 5분마다 51회였다.
무료 플랜의 분당 한도에 가까워 실패 위험이 있었다. 기본 도시를 권역이 겹치지 않는
다섯 곳으로 줄여 15회로 낮췄다. 나머지 도시는 검색으로 추가할 수 있으므로 기능이 줄지는 않는다.

### 동작은 하는데 티가 나지 않던 경우

**한 글자 칠 때마다 검색 결과 목록이 떴다.**
입력 이벤트에서 바로 조회를 부르고 있었다. 목록 필터는 글자마다 반응해야 맞지만
외부 조회까지 같이 부를 이유는 없었다. 목록 필터는 그대로 두고,
외부 조회는 Enter와 찾기 버튼에서만 부르도록 분리했다.

**카드를 골라도 아무 일도 일어나지 않는 것처럼 보였다.**
선택된 카드와 마우스를 올린 카드가 둘 다 테두리 색만 바뀌어 구분이 되지 않았고,
선택의 결과인 주간 예보 패널은 화면 아래쪽에 있어 눈에 들어오지 않았다.
선택 표시를 두 겹 테두리로 바꾸고, 카드를 고르면 **그 자리에서** 항목별 점수 근거가
펼쳐지도록 했다. 함께 있던 상세보기도 회색 잔글씨라 버튼으로 보이지 않아 형태를 바꿨다.

**정렬 바의 입력칸이 아무 동작도 하지 않았다.**
컴포넌트는 변경 이벤트를 올리고 있었지만 받는 쪽에서 연결하지 않아 값이 흘러가지 않았다.
위쪽 검색창이 이미 같은 역할을 하고 있어서 중복 입력칸을 제거하는 쪽으로 정리했다.
